# Vibe 专用 Idea 基础体检清单(11 维逐条)

> 本文件是 `vibe-idea` 的**基础体检层详解**。

## 定位

**先体检——确保 idea 不是伪需求、边界清晰。** 这是**拔高的前提**:连真痛点、真用户、真边界都没站稳的点子,拔得再高也是空中楼阁。下面 11 条**每条都是一个必须被覆盖的维度**。

## 覆盖方式约定

覆盖方式有二:用户已答(打勾),或 `vibe-idea` 补问后得到答案。无法回答的,转入「关键假设」登记并标注风险等级,**不允许**留空、也不允许用「待定」一类的空字样搪塞。每个维度在 `idea.md` 中都有对应章节,且必须留下「已确认结论」或「列为假设 / 风险」二者之一的可追溯记录。

---

## 11 个维度

### 1. 痛点与真实性

**维度问题**:要解决的具体问题是什么?谁正在为它付出代价 / 绕路 / 花钱?有没有「现在就有人这么干」的证据?

*为什么问*:伪需求是 Vibe 项目最大的沉没成本来源;先证真痛点,后面所有设计才有锚。

**喂给下游**:作为整份 `idea.md` 的锚,所有下游设计据此判断功能是否服务真痛点。

### 2. 目标用户与画像

**维度问题**:主要用户是谁(角色 / 规模 / 技术水平 / 付费意愿)?是否有次要用户或多边角色?

*为什么问*:用户画像决定交互复杂度、文案语气与平台选择。

**喂给下游**:是 `interaction.md` 的**隐性输入**(交互复杂度、文案语气)。

### 3. 核心场景与使用频率

**维度问题**:用户在什么情境下、多久用一次、为完成什么任务而打开它?高频还是低频?

*为什么问*:频率决定产品形态(高频 → 常驻 App,低频 → 网页 / 工具)与留存设计。

**喂给下游**:直接影响 `vibe-interaction`(以及其后 `vibe-architecture`)后续页面与主流程取舍。

### 4. 差异化价值

**维度问题**:现有替代方案(包括「用 Excel / 微信群 / 不做」)是什么?我们凭什么更好?一句话价值主张?

*为什么问*:没有差异化的产品在设计阶段会无限堆功能;先定差异化才能在 MVP 阶段做减法。

**喂给下游**:为 MVP 边界(维度 5)提供做减法的依据。

### 5. MVP 边界与 YAGNI

**维度问题**:第一版**必须有**的功能 / **明确不做**的功能各是什么?最小可验证闭环是哪条路径?

*为什么问*:这是 `vibe-interaction` 页面清单与 `vibe-prototype` 出图范围的总闸门;边界不清会导致下游无限膨胀。

**喂给下游**:`vibe-interaction` 页面清单与 `vibe-prototype` 出图范围的**总闸门**。

### 6. 成功指标

**维度问题**:上线后用什么可量化信号判断「成了」(激活 / 留存 / 转化 / 任务完成率 / 某北极星指标)?

*为什么问*:指标反向约束 MVP 必做功能。

**喂给下游**:让 `vibe-implement` 知道哪些埋点 / 数据是刚需。

### 7. 平台与技术约束

**维度问题**:目标平台(iOS / Android / Web / 小程序 / 桌面 / CLI)、必须兼容的环境、团队已有技术栈或硬性限制?

*为什么问*:决定其可选技术栈空间与原型尺寸 / 适配方案。

**喂给下游**:这是给其后的 `vibe-architecture`(排在 `vibe-interaction` 之后)的**约束输入(不是技术决策)**。

### 8. 商业模式

**维度问题**:免费 / 订阅 / 一次性买断 / 广告 / 抽成 / 纯自用?是否近期需要收钱?

*为什么问*:付费墙、账号体系、合规要求都会反推出额外页面与接口。

**喂给下游**:早定可避免 `interaction.md` 返工。

### 9. 数据与隐私 / 合规

**维度问题**:涉及哪些用户数据(尤其敏感 / 个人信息)?是否触及实名、支付、未成年人、医疗、跨境等监管?

*为什么问*:合规要求是硬约束,会直接产生强制页面(隐私协议、授权弹窗、注销入口)与后端设计要求,漏了是法律风险。

**喂给下游**:**强制**地塑造 `vibe-interaction` 页面与 `vibe-architecture` 后端设计。

### 10. 关键假设与最大风险

**维度问题**:这个 idea 成立依赖哪些尚未验证的假设?如果只有一件事可能让它失败,是哪件?

*为什么问*:把「不确定」显性化,既驱动 MVP 优先验证最大风险。

**喂给下游**:随 `idea.md` 沿流水线下传的**风险清单**(`vibe-interaction` 据此排布主流程与边界态,其后 `vibe-architecture` 据此做技术取舍)。

### 11. 非功能需求(性能 / 规模 / 离线 / 国际化 / 可访问性)

**维度问题**:预期并发 / 数据量级?是否需离线可用?多语言?无障碍?响应速度的体感底线?

*为什么问*:非功能需求会从根上改变交互与架构(如离线 → 本地存储与冲突合并、i18n → 文案外置与布局弹性),晚发现代价极高。

**喂给下游**:从**根上**改 `vibe-interaction` 交互与其后的 `vibe-architecture` 架构。

---

## 清单使用约定(结尾)

- 每个维度在 `idea.md` 中都有对应章节,并留下可追溯记录(「已确认结论」或「列为假设 / 风险」)。
- 无法回答的转入「关键假设」并标风险等级,**不允许留空、不允许用「待定」一类空字样搪塞**。
- 体检通过后,**务必进入拔高层**(四透镜,见 `ai-era-product-framework.md`),不在体检结束就收工——体检只保证「这个点子站得住」,**拔高**才回答「这个点子值不值得做、能不能更狠」。
